### 1. EXECUTIVE SUMMARY

*   **Total Attack Surface**: 85+ exposed methods across three primary interfaces (`AndroidList`, `AndroidPlan`, `AndroidMap`).
*   **Risk Posture**: **CRITICAL**. The application exposes a broad API surface to the WebView that includes file system interactions, flight plan management, and navigation state manipulation. The interface naming convention suggests a lack of strict input validation, and the sheer volume of methods (many redundant) suggests "Interface Bloat," significantly increasing the probability of unintended side effects or RCE through method overloading/reflection abuse.

### 2. CRITICAL VULNERABILITY FINDINGS

#### **Title: Arbitrary File System Traversal / Injection via `importFromFile`**
*   **Risk Level**: **Critical**
*   **Data Flow Path**: [JS `importFromFile(string)`] -> [`AndroidList.importFromFile(String)`] -> [Java File System Sink]
*   **Technical Description**: The method `importFromFile(String)` accepts a string parameter representing a filename or path. If this parameter is not strictly sanitized against Directory Traversal patterns (e.g., `../../`), an attacker who gains control over the WebView (via XSS or an insecure remote URL) can force the application to import or potentially overwrite arbitrary files within the application’s private data directory or shared storage.
*   **Evidence**: `AndroidList` exposes `importFromFile(Ljava/lang/String;)V` in both `WebAppAircraftInterface` and `WebAppListInterface`.

#### **Title: Command Injection / Logic Manipulation via `doAction`**
*   **Risk Level**: **High**
*   **Data Flow Path**: [JS `doAction(string)`] -> [`AndroidMap.doAction(String)`] -> [Java `doAction` implementation]
*   **Technical Description**: The `doAction(String)` method is a classic "God Method" anti-pattern. If the string passed to `doAction` is used as a selector for a switch-case statement or reflection-based lookup to execute internal logic, it provides an entry point for an attacker to trigger administrative or hidden functions simply by fuzzing strings. If `doAction` parses the string into a command object or a file path, it acts as a primary sink for arbitrary command execution.
*   **Evidence**: `AndroidMap` exposes `doAction(Ljava/lang/String;)V`.

#### **Title: Unrestricted Plan Manipulation and Injection**
*   **Risk Level**: **High**
*   **Data Flow Path**: [JS `amendPlan(...)`] -> [`AndroidPlan.amendPlan(...)`]
*   **Technical Description**: The `amendPlan` method accepts 24 string arguments. This is highly indicative of insecure deserialization or a lack of input validation. If these strings are concatenated into a SQL statement or an Intent, it is susceptible to SQL Injection (SQLi) or Intent Redirection. An attacker could overwrite flight plan metadata, potentially leading to incorrect navigational data or application crashes by providing malformed or malicious payload strings.
*   **Evidence**: `AndroidPlan` exposes `amendPlan` with 24 `String` arguments.

### 3. REMEDIATION STEPS

1.  **Restrict Interface Exposure**: 
    *   Audit all 85+ methods. Remove any method not explicitly required by the frontend. 
    *   Implement **Principle of Least Privilege**: Create a "Bridge Controller" that acts as a gatekeeper, rather than exposing entire service classes directly via `addJavascriptInterface`.

2.  **Input Validation & Sanitization**:
    *   **Path Traversal**: For `importFromFile` and `save...` methods, implement a strict allow-list for file extensions and canonicalize the resulting path using `File.getCanonicalPath()` to ensure the file resides in the expected directory.
    *   **String Payloads**: For methods like `amendPlan` and `saveList`, implement regex-based validation to reject special characters (`../`, `'`, `--`, `;`) that could lead to injection.

3.  **Use Annotations**:
    *   Ensure all methods exposed to JS are annotated with `@JavascriptInterface` (mandatory for API 17+).
    *   Verify that `WebView.getSettings().setAllowFileAccess(false)` and `setAllowContentAccess(false)` are set to minimize the impact of a compromised bridge.

4.  **Security Token/Handshake**:
    *   Require the JS layer to pass a secure, time-limited token (generated by the native side) with every sensitive bridge call to prevent XSS-based "drive-by" native calls.
